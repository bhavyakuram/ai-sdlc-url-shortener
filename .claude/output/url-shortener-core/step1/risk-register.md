# STEP-1 Discovery: Risk Register — url-shortener-core

**Phase:** STEP-1 · **Agent:** `risk-analysis`
**Stack:** java-spring · **Role:** greenfield · **Mode:** agentic · **Platform:** none
**Inputs read:** `step1/feasibility-report.md` (this run's Parts 1-3, above),
`prework/prd-v0.md` (all 12 FRs, 6 NFRs, 3 STEP-3 friction points)

## Method
Every risk below is derived from a specific FR/NFR in `prework/prd-v0.md` or a specific finding in
`step1/feasibility-report.md` — none are generic boilerplate ("could have bugs"). Likelihood and
Impact are each rated Low/Medium/High; **Severity = Likelihood x Impact** on a 3x3 grid
(Low x Low = Low, High x High = Critical, everything touching one High axis = at least Medium).
This register does not gate STEP-1 by itself (`rules/quality-gates.md`'s BLOCKER/HIGH severity
bands apply at STEP-4.1 build-verdict and STEP-6, not here) — it exists so STEP-3's technical
design has real, named risks to design against instead of discovering them at generation time.

## Risk Register

| ID | Risk | Source | Likelihood | Impact | Severity | Mitigation |
|---|---|---|---|---|---|---|
| R-1 | **H2 defaults to in-memory mode** (Spring Boot auto-config default is `jdbc:h2:mem:...`), silently violating FR-5's durability requirement and the NFR "0 link records lost across a normal process restart" — the failure mode is silent because the app still runs correctly right up until a restart. | `feasibility-report.md` Part 1, condition #1 | Medium (an easy default to leave unchanged if not called out explicitly at STEP-3) | High (violates a Must-Have NFR, data loss on every restart, not a degraded-mode failure) | **High** | STEP-3 technical design must explicitly specify `jdbc:h2:file:<path>` in `application.yml`, and STEP-4's generator output must be checked at build-verdict/STEP-5 time for the literal `mem:` vs `file:` URL scheme — not just "H2 is configured," but "H2 is configured in file mode." Add an integration test that restarts the datasource (or re-opens the file) and asserts a previously-created link still resolves. |
| R-2 | **Collision/concurrency race on code generation** (FR-4) — two concurrent creation requests generate the same base62 code before either has committed; if collision handling is implemented as check-then-insert (`SELECT` then `INSERT`) instead of relying on the DB unique constraint, the check-then-insert window is a genuine TOCTOU race under concurrent load, directly violating the NFR "Collision rate: 0 duplicate active codes ever persisted, under concurrency." | `prework/prd-v0.md` FR-4, NFR table; `feasibility-report.md` Part 1 FR-4 row | Low-Medium (only manifests under real concurrent load, which unit tests without concurrency won't catch) | High (a silently-corrupted redirect — code points to the wrong long URL — is a correctness failure, not a crash, and may not be noticed until a user reports it) | **High** | STEP-3/STEP-4 must implement collision handling as **insert-then-catch** (`@Column(unique = true)` + catch `DataIntegrityViolationException`, retry with a new code), never check-then-insert. STEP-5 validation must include an actual concurrent-request test (e.g. N parallel threads submitting the same custom code, or enough parallel generated-code requests to make a collision plausible against the 7-char base62 keyspace), not just sequential unit tests — `rules/testing.md`'s Test Independence rule still applies (no shared mutable fixtures across test classes), but this specific test needs real concurrency, not a mock. |
| R-3 | **No stable virtual threads on Java 19** (Spring Boot 3.1.4-3.2.x does not enable Loom-based virtual threads out of the box on this JDK) — redirect-path concurrency and the FR-9 rate limiter must run on Tomcat's conventional bounded thread pool. At the MVP's stated scale this is adequate, but it is a real ceiling that wasn't there under the originally-assumed Java 21/virtual-threads model. | `prework/prd-v0.md` Section 2.5 friction #1; `market-research.md` Section 3.2 point 1 | Low (a 100 req/min-per-code rate ceiling per FR-9 is far below default Tomcat thread-pool exhaustion, and there's no stated requirement to handle traffic beyond that) | Medium (if exceeded, degrades to request queuing/timeouts under load, not data corruption — but would directly threaten the p95 < 50ms redirect-latency NFR) | **Medium** | STEP-3 must explicitly design against the conventional thread-pool model (document the assumption, size the Tomcat pool deliberately) rather than silently assuming virtual-thread-style scaling. If load ever needs to exceed thread-pool capacity, that is a future capacity-planning decision (JDK upgrade path to enable Loom), not a v1 blocker — flagged here so it isn't rediscovered as a surprise at STEP-6 performance review. |
| R-4 | **Rate-limiter implementation risk** (FR-9) — Spring Boot has no first-party rate limiter; `dependency-audit`'s Part 2 recommends Bucket4j 8.19.0, but if STEP-3/STEP-4 instead hand-rolls a token bucket under time pressure, a naive implementation (e.g. non-atomic read-modify-write on a shared counter) can under- or over-count under concurrent redirects on the same code, either leaking past the 100 req/min ceiling (defeating FR-9/the abuse-resilience NFR) or false-positive 429-ing legitimate traffic. | `prework/prd-v0.md` Section 2.5 friction #2; `feasibility-report.md` Part 2 friction point #2 | Medium (concurrency bugs in hand-rolled rate limiters are a well-known class of mistake; even with Bucket4j chosen, misconfiguring the bucket's refill/key strategy is possible) | Medium (a leaky rate limiter is an abuse-resilience gap, not data corruption; a false-positive rate limiter is a functional regression on legitimate traffic) | **Medium** | Use Bucket4j (per `dependency-audit` Part 2) rather than hand-rolling, specifically because its bucket operations are already documented as thread-safe/atomic — reduces this risk rather than introducing a new one. STEP-5 must include a concurrent-request test against the rate limiter (burst above 100 req/min in a short window, assert exactly the expected count of 429s), matching the NFR's explicit "10x threshold flood -> no 5xx" requirement — a 429 is correct, a 5xx under the same flood is not. |
| R-5 | **Geo-IP capability not yet in the stack manifest's declared vocabulary** (FR-10) — `stacks/java-spring/stack-manifest.md` currently declares `api:rest`, `services:jvm`, `data:relational`, `build:maven`, `test:junit` only. If STEP-4's `generator` adds the MaxMind dependency without STEP-3 first adding a capability token (e.g. `data:geoip-offline`) to the manifest, this is a `rules/architecture.md` Technology Agnosticism / capability cross-check violation waiting to be caught late (at `stack-validator`'s next run or STEP-6 static analysis) instead of designed for up front. | `prework/prd-v0.md` Section 2.5 friction #3; `feasibility-report.md` Part 2 friction point #3 | Medium (this is a process/governance risk, not a technical one — it only manifests if STEP-3 skips the manifest update) | Medium (caught mechanically at the next `stack-validator` capability cross-check either way, so it can't silently ship, but it does cost a rework cycle / retry-budget unit if caught late instead of at STEP-3) | **Medium** | STEP-3 technical design must explicitly add the new capability token to `stacks/java-spring/stack-manifest.md` alongside naming the MaxMind dependency (both actions in the same design step, not sequenced), so `stack-validator`'s capability cross-check passes on the first STEP-4 attempt rather than bouncing back. |
| R-6 | **H2 web console left enabled exposes an unauthenticated RCE surface** (CVE-2021-42392, JNDI/LDAP injection via the H2 Console) directly compounded by FR-6's hard no-auth-layer constraint — on most Spring Boot services an exposed admin console is bad but sits behind some other perimeter control; here there is no login/session concept anywhere in the request path by design, so a left-on console would be reachable exactly as easily as every other endpoint. | `feasibility-report.md` Part 2, H2 CVE note | Low (the console is off by default in Spring Boot unless `spring.h2.console.enabled=true` is explicitly set — this requires an active misconfiguration, not a passive default) | Critical (unauthenticated RCE, and FR-6 means there is no secondary auth layer to catch the mistake — full compromise of the process, not just data exposure) | **High** (Low likelihood x Critical impact — per this register's own severity grid, any Critical-impact risk floors at High severity regardless of likelihood, since the downside is total compromise) | Pin `com.h2database:h2` to >= 2.2.220 (closes CVE-2021-42392 and CVE-2022-45868 regardless). Explicitly set `spring.h2.console.enabled=false` in every non-local profile at STEP-3/STEP-4 (don't rely on "it's off by default" — state it), and STEP-6.2 `security-audit` should specifically check for this flag's value in any non-dev config file, given `rules/security.md`'s Zero-Regression Posture treats any new HIGH/CRITICAL finding as a BLOCKER. |
| R-7 | **MaxMind GeoLite2 license key is an operational dependency with a 90-day expiry**, not a one-time setup — the `.mmdb` database file that FR-10's geo lookup depends on is not a Maven artifact; it requires a MaxMind account, an accepted EULA, and a license key that expires every 90 days without reconfirmation (per live search, confirmed in `dependency-audit` Part 2). A stale key silently breaks the download/refresh pipeline for the country database without breaking the build, tests, or any other FR. | `feasibility-report.md` Part 2, friction point #3 concrete pick | Medium-High **over time** (a 90-day recurring credential-rotation task is exactly the kind of manual step that gets missed; low likelihood in the first 90 days, rising with every renewal cycle after) | Low-Medium (FR-10's stats endpoint degrades to missing/stale country data — the core redirect/create functionality, FR-1/FR-2, is entirely unaffected, since geo lookup is a side-effect of a successful redirect, not a precondition for one) | **Medium** | STEP-3 must document the `.mmdb` refresh as an explicit operational runbook item (not just a one-time build step), and the geo-lookup call site must fail soft (log + omit country, per `rules/coding-standards.md`'s No Silent Catches — log with context, don't crash the redirect) if the database file is missing/stale, so R-7 materializing degrades FR-10 only, never FR-2. Credential storage must follow `rules/security.md` Credential Hygiene (license key never in generated source, tests, or `_run-log.md`). |
| R-8 | **Unbounded in-process rate-limiter state growth** — FR-9's bucket is keyed by (source-IP, short-code); with no accounts and no cap on distinct codes or IPs (FR-6), a sustained flood of unique (IP, code) pairs (including a spoofed-IP variant, or simply many distinct real callers hitting many distinct links) grows the in-memory bucket map without bound, since nothing in the FR set specifies eviction. | Derived from FR-9 + FR-6's combination (no independent source in PRD — this is this register's own analysis, flagged as such) | Medium (an anonymous, no-rate-limited-by-account service is an easy target for exactly this kind of low-effort resource-exhaustion probing) | Medium (a memory-growth DoS is a service-degradation risk, not a data-integrity one — matches the NFR's own framing of "abuse resilience" as the relevant concern) | **Medium** | STEP-3 must specify a bounded/expiring backing store for the rate-limiter state (e.g. Bucket4j's built-in expiration policies, or a bounded cache like Caffeine with a TTL matching the 1-minute window) rather than an unbounded `ConcurrentHashMap`. This is a design detail worth naming now precisely because it's easy to omit when the FR text only specifies the *limiting* behavior, not the *storage* behavior. |
| R-9 | **Open-redirect / abuse-of-service risk is inherent to the product, not a bug** — FR-3 validates URL *shape* (scheme + length) but not URL *reputation*; any anonymous caller can create a short link to any http(s) destination, including phishing/malware targets, and the resulting short URL inherits this service's own domain reputation. This is explicitly out of scope per PRD (concept.md W1-W5 lists no allowlist/reputation feature), but it is a real risk this register should name rather than let go unrecorded just because it's an accepted trade-off. | `prework/prd-v0.md` FR-3, Explicitly Out of Scope list; general property of anonymous open URL shorteners (also implicit in `market-research.md`'s Bitly/TinyURL/YOURLS comparison — all three face the same exposure) | High (this is not a hypothetical — anonymous, no-account URL shorteners are a known abuse vector in the wild) | Medium (reputational/abuse risk to the service and to whoever eventually deploys it operationally — not a data-integrity or availability risk to the service itself) | **Medium-High** | No code mitigation is in scope for v1 (explicitly out of scope per PRD). Recorded here as an **accepted risk requiring explicit operator sign-off at Gate 2/Gate 3**, not silently absorbed — if this framework's operator wants a mitigation (e.g. a blocklist check against a known-malicious-URL feed), that is a new FR for a future increment, not something `generator` should improvise unprompted at STEP-4. |
| R-10 | **Declared vs. actual JDK/Spring Boot version drift** — `stack-manifest.md`'s "Identity" section still states Java 21 while its own "Versions" section documents a STEP-4 correction to Java 19 / Spring Boot 3.2.x because the only available JDK on the dev machine is 19. This inconsistency within the manifest itself is a minor documentation risk, but it also means any environment that *does* have JDK 21 available could silently build against a different baseline than what was actually verified. | `stacks/java-spring/stack-manifest.md` Identity vs. Versions sections (self-inconsistent as read) | Low (single-developer/single-environment context today; only manifests if a second environment with a different JDK enters the picture) | Low (a version mismatch would surface immediately at build-verdict time — `rules/build-green.md`'s IDE/Compiler Is the Build Oracle rule means this fails loud, not silent) | **Low** | Recommend `stack-manifest.md`'s "Identity" section be corrected to Java 19 to match "Versions" (a documentation fix, not a code risk) so future runs don't have to re-derive which section is authoritative. Not blocking STEP-1 completion — flagged for STEP-3/operator awareness. |

## Overall Risk Level: **MEDIUM**

**Reasoning:** Zero Critical risks and zero unmitigated High risks — every High-severity item
(R-1, R-2, R-6) has a concrete, named mitigation that STEP-3/STEP-4 can implement directly (file-mode
config, insert-then-catch collision handling, console-disabled + version pin), not an open
question requiring new invention. Nothing here rises to a feasibility blocker (consistent with
`feasibility-report.md` Part 1's BUILDABLE verdict). The register's overall posture is Medium
rather than Low because of the combination of (a) three concurrency-shaped risks (R-1 durability,
R-2 collision, R-8 rate-limiter state) that are easy to get subtly wrong under load and won't
necessarily fail a naive sequential test suite, and (b) one real operational/governance risk with
no code fix (R-7's 90-day license-key rotation) that must be tracked outside the codebase. **Two
items need explicit operator/Gate-2 sign-off rather than silent STEP-3 absorption: R-7 (accepting
an external credential-rotation dependency for FR-10) and R-9 (accepting open-redirect abuse
exposure as an out-of-scope trade-off for v1).**
